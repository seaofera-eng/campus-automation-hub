## 새 권한 모델

지금은 역할 하나(`REQUESTER`/`DEVELOPER`/`REVIEWER`/`ADMIN`)가 권한과 신분을 겸하고 있다.
이것을 **권한**과 **신분** 두 축으로 나눈다.

### 축 1 — 계정 종류 `AccountType`

```
USER   이용자. 수요도 등록하고 도구도 등록한다. 둘을 나누지 않는다.
ADMIN  관리자.
```

리뷰 3절: *"이용자 모두가 수요자이자 개발자임"* · 11절: *"모든 사용자는 수요자이면서 개발자 역할을 할 수 있어야 함"*

### 축 2 — 관리자 세부 권한 `AdminPermission`

`ADMIN` 계정만 가진다. 관리자라고 전부 다 할 수 있는 게 아니다.

```
REVIEW            도구 검토 · 위험 체크리스트 · 검토 상태 전환 · 수요-도구 연결
MANAGE_USERS      계정 권한 변경 · 활성/비활성
MANAGE_CATEGORIES 카테고리 관리
MANAGE_TOOLS      사용 중지 · 폐기
MANAGE_NOTICES    공지 작성
VIEW_AUDIT        감사 로그 열람
```

리뷰 9.5절: *"관리자에게 어느 정도 권한까지 접근이 가능한지 구분"*

### 축 3 — 이용자 신분 `MemberType`

권한이 **아니다**. 회원가입 구분과 "추천 수요자" 표시에 쓴다.

```
STUDENT    학생
STAFF      교직원
PROFESSOR  교수
EXTERNAL   일반인
```

리뷰 2절(회원가입 구분) · 4.1절(추천 수요자) · 5.1절·6.1절(목록에 수요자 표기)

### 소유권 규칙은 그대로

"자기가 만든 도구/수요만 고칠 수 있다"는 규칙은 권한 축과 무관하게 유지한다.

**1단계에서 새로 정한 것**

- **관리 권한은 운영 권한이지 저작 권한이 아니다.** 예전에는 관리자가 모든 동작을
  통과했다. 그러면 관리자가 남의 도구 설명이나 남이 쓴 평가를 고칠 수 있다.
  소유권으로 갈리는 동작(`tool:update`·`demand:update`·`evaluation:update` 등)은
  관리 권한으로 넘지 못하게 두었다.
- **검토와 정식 승인을 다른 권한으로 나눴다.** 검토(`REVIEW`)는 시범운영 승인까지,
  정식 승인·사용 중지·폐기는 도구 운영(`MANAGE_TOOLS`). 검토한 사람이 혼자
  끝내지 못하게 하는 이중 확인이다. 예전 모델에서 정식 승인이 관리자 전용이던 것과 같은 취지.
- **권한 없는 관리자 계정은 이용자와 같다.** 계정 종류만으로 문이 열리면 세분화한 의미가 없다.
- **공개 범위와 부서 칸막이를 없앴다.** 남은 구분은 "작성 중인 임시저장은 만든 사람만 본다" 하나뿐.
