# 설계 결정 기록

되돌리기 전에 읽어야 할 결정들입니다. 대부분 실제로 문제를 겪고 내렸습니다.

## 툴체인

### ESLint 는 9.39.5 에 고정한다. 10.x 로 올리지 말 것

ESLint 10 이 `context.getFilename()` 을 제거했는데 `eslint-plugin-react@7.37.5`
(eslint-config-next 16 의 의존성)가 이를 호출합니다. `pnpm lint` 가
`TypeError: contextOrFilename.getFilename is not a function` 으로 **전면 실패**합니다.

### TypeScript 는 5.9.3 에 고정한다. 7.x 로 올리지 말 것

TS 7 은 네이티브 포팅 릴리스라 `typescript-eslint@8` 타입인지 규칙과의 호환
리스크가 있습니다. 5.9 는 Next 16·Vitest 와 검증된 조합입니다.

### pnpm 은 `npm i -g pnpm` 으로 설치한다

Windows 에서 `corepack enable` 이 `C:\Program Files\nodejs` 쓰기 권한 없이
`EPERM` 으로 실패합니다.

### Tailwind 는 v4 CSS-first. `tailwind.config.js` 를 만들지 말 것

토큰은 `src/app/globals.css` 의 `@theme` 블록에 있습니다.

### shadcn CLI 를 쓰지 않는다

`radix-ui` 통합 패키지 + CVA 로 `src/components/ui/` 에 직접 vendoring 했습니다.
CLI 의 대화형 init 과 레지스트리 네트워크 의존을 피해 재현성을 확보하기 위함입니다.

### 차트 라이브러리를 넣지 않는다

대시보드 분포는 CSS 막대 + 숫자 라벨 + `<table>` 마크업입니다.
"색만으로 구분하지 않는다"(요구사항 12번)와 맞고, 스크린리더가 표로 읽을 수
있으며, 번들도 가볍습니다.

## 구조

### domain 계층은 아무것도 import 하지 않는다

상태 전환과 권한은 가장 바뀌면 안 되는 규칙입니다. 프레임워크나 저장소에 딸려
있으면 테스트하기 어렵고 "화면에서 이렇게 하니까"라는 이유로 규칙이 흔들립니다.
ESLint `no-restricted-imports` 가 강제합니다.

### UI 는 저장소를 직접 호출할 수 없다

권한 검사와 감사 로그를 우회할 수 없게 하기 위해서입니다.
ESLint 가 `@/repositories/*` import 를 차단합니다.

### DEMO/Supabase 분기는 두 곳에만 둔다

`lib/di/container.ts` 와 `lib/auth/current-user.ts`.
서비스와 UI 코드에는 `DEMO_MODE` 분기가 없습니다.

### 검증 스키마를 서버와 클라이언트가 공유한다

규칙을 두 벌 관리하면 반드시 어긋납니다. 클라이언트 검증은 어느 칸이 문제인지
빨리 알려 주기 위한 편의이고, 실제 차단은 항상 서버가 합니다.

### 통합 테스트는 서버 액션이 아니라 application 서비스를 부른다

액션은 `next/headers` 에 의존해 Vitest 에서 동작하지 않습니다. 실제 규칙은
전부 application 계층에 있으므로 검증 범위는 줄지 않습니다.

### Vitest 에서 `server-only` 를 빈 모듈로 바꾼다

이 패키지는 Next.js 밖에서 import 하면 무조건 예외를 던집니다.
서버 전용 경계의 실제 검사는 `pnpm build` 가 계속 담당합니다.

## 실제로 겪고 고친 것

### `app/(app)/tools/` 에 `loading.tsx` 를 두지 않는다

세그먼트에 로딩 경계를 두면 **하위 경로까지 내려갑니다.** 응답 헤더가 먼저
나가 버려서 `/tools/[id]` 와 `/tools/new` 의 `notFound()` 가 **404 대신 200 을
반환**했습니다. 화면 내용은 "페이지를 찾을 수 없습니다"로 맞았지만 상태 코드가
틀렸습니다.

목록 페이지 안의 `<Suspense>` 로 바꿔 해결했습니다.

### 권한 없음을 404 로 보여준다

"권한이 없습니다"라고 알려 주면 그 항목이 **존재한다는 사실**이 새어 나갑니다.
목록에서 걸러진 도구의 주소를 하나씩 찍어 보며 존재 여부를 확인하는 것을 막습니다.

### 평가·개선 요청 버튼을 탭 안에 두지 않는다

radix Tabs 는 비활성 탭을 언마운트합니다. 처음엔 평가 버튼을 평가 탭 안에
넣었는데, 탭을 눌러야만 보이니 "이 도구 어땠나요"를 물을 기회를 놓칩니다.
상단 액션 영역으로 옮겼습니다.

### "마지막 관리자 보호" 검사를 넣었다가 뺐다

이 함수를 부르려면 행위자가 관리자여야 하고 자기 역할은 못 바꾸므로, 어떤
경우에도 행위자가 관리자로 남습니다. **한 번도 정상 발동할 수 없는 코드**였습니다.

게다가 부작용이 있었습니다 — 비활성 관리자를 정리하려 하면 집계에서 그 사람이
빠져 "마지막 관리자"로 오판해 정상 작업을 막았습니다.

### 평가 점수 라디오에 `aria-label` 을 붙였다

숫자와 라벨이 별개의 `<span>` 이라 접근성 이름이 "4우수"로 붙어 읽혔습니다.
`aria-label="4점 우수"` 로 명시했습니다. E2E 를 쓰다가 발견했습니다.

### `store.ts` 의 `turbopackIgnore` 주석

없으면 Turbopack 이 `process.cwd()` 를 보고 프로젝트 전체를 추적 대상으로 잡아
빌드 경고를 냅니다.

## 표시 원칙

### 평가가 없으면 0점이 아니라 "평가 없음"

0점은 "나쁜 평가를 받았다"로 읽힙니다.

### 비용은 0원과 "파악하지 못함"을 구분한다

무료인 것과 안 알아본 것은 다릅니다. 폼에서도 빈 칸을 `null` 로 저장하고
0 으로 채우지 않습니다.

### 상태는 텍스트 + 아이콘 + 색 3중으로 인코딩한다

색각 이상이 있거나 흑백으로 인쇄해도 의미가 전달되어야 합니다.
아이콘 없이 색만으로 구분되는 배지를 만들지 않습니다.

### 빈 상태에는 다음 행동을 넣는다

`EmptyState` 는 `action` 을 선택 항목이 아니라 기본으로 받도록 설계했습니다.

## 로그와 알림

### 감사 로그에 값이 아니라 필드 이름만 남긴다

개인정보나 상담 내용이 로그로 새어 나가면 안 됩니다. 값이 필요하면 원본
테이블을 보면 됩니다.

예외는 **역할 변경 사유**입니다. 개인정보가 아니라 권한 변경의 근거이고,
그것을 남기는 것이 감사 기록의 목적입니다.

### 알림 본문에 사유나 요청 원문을 담지 않는다

알림은 목록에 오래 남습니다. "무슨 일이 있었는지"와 링크만 넣고 자세한 내용은
따라가서 보게 합니다.

### 실패한 작업도 감사 로그에 남긴다

권한이 없는 사람이 무엇을 시도했는지가 오히려 더 중요합니다.

## 데이터

### 평가는 버전에 붙는다

새 버전이 나오면 다시 평가받을 수 있고, "어느 버전에 대한 평가인지"가 분명합니다.

### 중복 평가를 세 겹으로 막는다

서비스 사전 확인 → DEMO 저장소 저장 직전 재확인 → Postgres 부분 유니크 인덱스.

### 데이터 분류를 불리언 8개가 아니라 행으로 저장한다

분류가 늘어날 때 스키마를 바꾸지 않아도 되고, 2단계 위험 평가가 이 행들을
그대로 입력으로 쓸 수 있습니다.

### 상태 이력을 트리거가 아니라 서비스에서 남긴다

트리거로 하면 DEMO 모드에서 같은 코드 경로를 쓸 수 없습니다.

### `.data/` 는 커밋하지 않는다

DEMO 로컬 데이터입니다. `pnpm demo:reset` 으로 초기화합니다.

### 역할 하나 대신 축 셋

이용자와 개발자를 나누지 않는다. 한 사람이 수요도 올리고 도구도 만든다.
남는 구분은 **소유권**(내가 만든 것인가)과 **관리 권한**(그 권한을 받았는가)뿐이다.

- `AccountType` — 이용자 / 관리자
- `AdminPermission` — 검토 · 계정관리 · 카테고리관리 · 도구운영 · 공지관리 · 감사로그 열람
- `MemberType` — 학생 / 교직원 / 교수 / 일반인 (**권한이 아니다**)

### 관리 권한은 운영 권한이지 저작 권한이 아니다

예전에는 관리자가 모든 동작을 통과했다. 그러면 관리자가 남의 도구 설명이나
남이 쓴 평가를 고칠 수 있다. 소유권으로 갈리는 동작(`tool:update`·`demand:update`·
`evaluation:update` 등)은 관리 권한으로 넘지 못하게 두었다.

### 검토와 정식 승인은 다른 권한

검토(`REVIEW`)는 시범운영 승인까지, 정식 승인·사용중지·폐기는 도구 운영(`MANAGE_TOOLS`).
검토한 사람이 혼자 끝내지 못하게 하는 이중 확인이다.

### 권한 없는 관리자 계정은 이용자와 같다

계정 종류만으로 문이 열리면 권한을 세분화한 의미가 없다.

### 부서와 공개 범위를 없앴다

부서로 칸막이를 치면 옆 부서가 이미 만든 도구를 못 찾아 같은 것을 또 만든다.
공개 범위도 부서가 사라지면서 판단 근거를 잃었다. 남은 구분은
**"작성 중인 임시저장은 만든 사람만 본다"** 하나뿐이다.

### 평가는 익명이다

개발자와 수요자가 서로 아는 학내 플랫폼에서 실명 평가는 솔직한 이야기를 막는다.
작성자는 저장하되(중복 방지·본인 수정) 화면에 표시하지 않는다.

### 토큰 원장은 append-only

잔액 컬럼을 두지 않고 기록을 더해서 계산한다. 잔액만 들고 있으면
"왜 이 숫자가 됐는지"를 못 밝힌다. 차감 개념이 없어 음수를 DB 제약으로 막았다.

### 권한 검사를 `<Suspense>` 안에서 하지 말 것

E2E 에서 실제로 겪었다. 검사가 Suspense 경계 안에 있으면 응답 헤더가 먼저 나가서
`notFound()` 가 **404 대신 200** 을 반환한다. `loading.tsx` 문제와 같은 원인이다.
페이지 컴포넌트 본문에서 먼저 `guardPage(() => requirePermission(...))` 을 부른다.
