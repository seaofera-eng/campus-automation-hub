# 결과보고서 (초안)

**캠퍼스 자동화 관제 플랫폼** — 교내 AI·업무 자동화 도구 통합 관리 플랫폼

> 초안입니다. 제출 전에 **분량과 표현을 대회 양식에 맞게 다듬어 주세요.**
> 숫자는 모두 2026-08-29 기준 실제 값이며, 근거 위치를 각 항목에 적어 두었습니다.
> 화면 그림은 `docs/demo-shots/` 에 20장 있습니다. 발표 순서는 [DEMO-SCRIPT.md](DEMO-SCRIPT.md).

---

## 1. 공모작(서비스) 개요

> 283자 (공백 포함) — 300자 이내

교내 구성원이 만든 AI·업무 자동화 도구를 한곳에 모아 등록·검토·평가·개선까지 관리하는
플랫폼입니다. 각 부서가 따로 만든 도구가 서로를 모른 채 중복되고, 개인정보를 다루는
도구가 검증 없이 쓰이는 문제에서 출발했습니다. 필요한 사람은 질문 다섯 개에 답해 이미
있는 도구를 찾고, 없으면 그 자리에서 요청합니다. 올라온 도구는 AI가 중복·품질·위험을
먼저 짚고, 사람이 다섯 단계로 확인해 승인합니다. 같은 도구를 두 번 만드는 낭비를 줄이고,
검증되지 않은 자동화가 학내에 퍼지는 것을 막습니다.

## 2. 창의성

### 2-1. 기존 서비스와 무엇이 다른가

| | 기존 방식 | 이 플랫폼 |
|---|---|---|
| **사내 위키·엑셀 목록** | 목록만 있고 검증이 없다. 최신인지 알 수 없다 | 상태·위험도·검토 이력이 도구에 붙어 다닌다 |
| **상용 AI 마켓플레이스** | 외부 서비스 카탈로그. 교내 데이터 취급 기준이 없다 | **교내에서 만든 것**이 대상. 다루는 데이터를 등록 단계에서 물어본다 |
| **AI 챗봇 단일 도입** | 도구 하나를 사서 쓴다 | 구성원이 **만든 것을 모으고 관리**한다 |
| **일반 결재·승인 시스템** | 문서를 올리고 결재를 받는다 | 결재 전에 **AI가 중복·품질·위험을 먼저 짚어** 검토자에게 넘긴다 |

핵심 차이는 하나입니다. **관리 대상이 문서가 아니라 "실제로 도는 자동화"라는 점**입니다.
그래서 "이미 같은 게 있는가", "이 도구가 어떤 데이터를 만지는가"를 시스템이 묻습니다.

### 2-2. 독창적인 요소

**① 중복을 등록 이후가 아니라 요청 단계에서 먼저 막는다**

대부분의 관리 시스템은 다 만들어 온 것을 검토합니다. 이 플랫폼은 **만들기 전에** 막습니다.
「맞춤 AI 찾기」 다섯 단계를 마치면 첫 화면이 **"이런 도구가 이미 있습니다"** 입니다.
아무것도 만들지 않고 끝나는 것이 이 플랫폼이 낼 수 있는 가장 좋은 결과입니다.

> 화면: `demo-shots/04-wizard-result.png`

**② 중복 탐지를 두 단계로 나눠 O(N²) 비용을 피한다**

도구가 N개일 때 모든 쌍을 LLM으로 비교하면 호출이 N² 로 늘어 감당이 안 됩니다.
그래서 **① 글자 3-gram 겹침으로 후보를 좁히고 → ② 그 후보만 모델 한 번**에 물어봅니다.
도구 하나를 등록할 때 LLM 호출은 **1회**입니다.

이 구조의 값어치는 실제 결과에서 드러납니다. 「미팅 노트 자동 정리기」 판정에서 모델은
**"회의 녹취록 텍스트"와 "회의 녹음 파일 또는 받아쓴 글"** 을 같은 것으로 묶었습니다.
낱말은 겹치지 않는데 **하는 일이 같다**는 것을 잡은 것으로, 글자 겹침 계산만으로는
불가능한 판단입니다.

> 화면: `demo-shots/12-review-step2-duplicate.png` (사실상 같은 도구 92점 · 기존 도구에 합치기)

**③ 서로 다른 모델 둘이 교차 검증하되, 판정이 갈리면 감추지 않는다**

`claude-opus-5` 와 `claude-sonnet-5` 가 등록 내용을 각각 다른 관점에서 봅니다.
두 모델의 판정이 다를 때 **평균을 내거나 다수결로 덮지 않고**, "두 모델의 판정이
갈렸습니다"라고 화면에 씁니다. 갈렸다는 사실 자체가 검토자에게 필요한 정보이기 때문입니다.

> 화면: `demo-shots/13-review-step3-quality.png`

**④ AI 제안으로 위험 체크리스트를 자동으로 채우지 않는다 (의도적 설계)**

기술적으로는 14개 항목을 AI 제안으로 미리 체크해 둘 수 있습니다. **그렇게 하지
않았습니다.** 채워 두면 검토자가 그대로 넘기기 때문입니다. AI 제안은 체크리스트
**위에 따로** 보여 주고, 표시는 사람이 합니다. 해당된다고 표시하면 **어떤 통제를
적용했는지 적어야** 저장됩니다.

> 화면: `demo-shots/14-review-step4-risk.png`, `demo-shots/15-risk-checklist.png`

**⑤ 순위에는 모델을 쓰지 않는다**

도구 순위는 만족도·실제 쓰임·안정성·안전·관리 **다섯 축의 순수 계산**입니다.
모델을 넣으면 "왜 이 순위냐"에 답할 수 없게 됩니다. 평가가 3건 미만이면
**「표본 부족 — 추천에서 제외」** 로 표시하고 추천하지 않습니다.

> 화면: `demo-shots/18-ranking.png`

**⑥ 분석을 화면에서 부르지 않는다**

AI 분석은 별도 스크립트가 미리 돌려 저장하고, 화면은 **읽기만** 합니다. 그래서
(가) 화면이 즉시 뜨고 (나) 같은 화면을 열 때마다 같은 결과가 나오며 (다) 비용이
예측됩니다. 예외는 수요 신청서 초안 다듬기 하나이고, 그마저 실패하면 규칙 기반
초안으로 끝까지 갑니다.

**⑦ 없는 것을 없다고 말한다**

분석을 돌리지 않았으면 **"아직 돌리지 않았습니다"** 라고 씁니다. 0으로 채우거나
흐린 숫자·자리표시용 그래프를 그리지 않습니다. 평가가 없으면 0점이 아니라
"평가 없음"입니다. **"없음"과 "파악하지 못함"을 구분**합니다.

**⑧ 감사 로그에 값이 아니라 필드 이름만 남긴다**

개인정보나 상담 내용이 로그로 새어 나가지 않도록, 무엇이 바뀌었는지(필드 이름)만
남기고 값은 저장하지 않습니다. **관리자 작업도 예외 없이** 기록합니다.

> 화면: `demo-shots/19-audit-log.png`

### 2-3. 운영 전략

- **개발자 토큰** — 수요를 해결해 준 구성원에게 토큰이 갑니다. 만드는 사람에게 돌아가는
  것이 있어야 계속 올라옵니다.
- **통합 표준화** — 중복 탐지가 도구 하나 단위라면, 통합 표준화 화면은 **묶음 단위**로
  비슷한 도구군을 찾아 통합 후보로 제시합니다.
- **개선 요청** — 쓰다가 불편한 점을 도구에 붙여 남기고, 그것이 순위의 '관리' 축에
  반영됩니다.
- **평가는 익명** — 저장은 하되(중복 방지·본인 수정) 화면에 작성자를 보여주지 않습니다.
  실명이면 같은 부서 도구에 낮은 점수를 주기 어렵습니다.

## 3. 활용성

### 3-1. 학내 정책·사업·시스템과의 연계

| 연계 지점 | 어떻게 맞물리는가 |
|---|---|
| **개인정보 보호 / 정보보안 정책** | 등록 단계에서 다루는 데이터 종류를 반드시 고르게 하고, 민감 분류를 고르면 즉시 경고합니다. 14항목 위험 체크리스트가 승인의 전제 조건이며, 위험도 '매우 높음'은 서버가 승인을 차단합니다 |
| **정보화 사업 중복투자 방지** | 부서별로 따로 발주·개발되던 자동화를 등록 시점에 대조합니다. 중복 판정에 「기존 도구에 합치기」 권고가 함께 나옵니다 |
| **업무혁신·행정효율화 과제** | 어떤 업무가 얼마나 반복되는지가 '업무 수요'로 쌓입니다. 수요 목록 자체가 자동화 우선순위 자료가 됩니다 |
| **기존 학사·행정 시스템** | 대체가 아니라 **위에 얹는 관제 계층**입니다. 도구는 각 시스템 앞단에서 돌고, 이 플랫폼은 그 도구의 등록·검증·이력을 관리합니다 |
| **교내 AI 게이트웨이** | 분석은 교내 AI 포털을 경유합니다. 외부 API 를 직접 부르지 않습니다 |

| **교육** | 강의 녹화 자막 추출·주차별 요약, 학사 규정 질의응답 | 강의 영상·음성, 학칙·지침 | 교무처, 학사관리과 |
| **연구** | 연구과제 공고 요약·맞춤 알림, 과제 서식 점검 | 공고문 PDF, 연구계획서 | 연구지원과, 산학협력단 |

    검토 시작 ──▶ ①도구 파악 ②중복 ③품질 ④위험 체크리스트 ⑤판단

### 3-4. 실현 계획

| 단계 | 기간 | 내용 |
|---|---|---|
| **1단계 — 시범 운영** | 1~2개월 | Supabase 연결, 교내 SSO 연동, 정보화본부 + 1~2개 부서 대상 시범. 기존 도구 목록 이관 |
| **2단계 — 확대** | 3~6개월 | 전 부서 개방. 위험 체크리스트 항목을 학내 정보보안 지침에 맞춰 조정. 검토자 지정·교육 |
| **3단계 — 정착** | 6개월~ | 수요 통계를 정보화 사업 기획에 연계. 통합 표준화 결과로 중복 도구 정리. 토큰 보상 제도화 |

**기술적 실현 가능성** — 저장소 인터페이스(메서드 96개)를 DEMO/Supabase **양쪽으로 이미
구현**해 두었고, PostgreSQL 마이그레이션 18개가 들어 있습니다. 환경변수 전환만으로
붙는 구조입니다. (다만 **실제 연결 검증은 아직 하지 않았습니다** — 4-5절 참조.)

### 3-5. 예상 성과

- **중복 개발 감소** — 요청 단계에서 기존 도구를 먼저 제시하므로, 같은 도구를 두 번
  만드는 일이 줄어듭니다.
- **미검증 자동화 차단** — 개인정보를 다루면서 접근통제·실행로그가 없는 도구가 승인
  단계에서 걸립니다.
- **자동화 수요의 가시화** — 흩어져 있던 "이거 자동화됐으면" 이 목록으로 쌓여 정보화
  사업 기획 자료가 됩니다.
- **책임 소재 명확화** — 누가 언제 무엇을 승인했는지가 상태 이력과 감사 로그에 남습니다.

> 정량 목표(예: 중복 개발 N건 방지)는 **시범 운영 전이라 제시하지 않습니다.**
> 근거 없는 숫자를 쓰지 않는 것이 이 프로젝트의 원칙이기도 합니다.

## 4. 완성도

### 4-1. 규모

| 항목 | 수치 |
|---|---|
| 소스 코드 | **243개 파일 · 36,706줄** (TypeScript / TSX) |
| 자동화 테스트 | **28개 파일 · 469개** 전부 통과 |
| 저장소 인터페이스 | 메서드 **96개** — DEMO·Supabase **양쪽 구현** |
| DB 마이그레이션 | **18개** (PostgreSQL + RLS) |
| 화면 | **25개 라우트** (`/_not-found`·`/api/health` 제외) |
| 감사 로그 대상 서버 액션 | **19개** |

### 4-2. 서비스 구조 — 계층 아키텍처

```
  화면 (app / components)          14,463줄   ← 서버 컴포넌트 + 클라이언트 컴포넌트
        │  서버 액션만 호출
  actions                            1,209줄   ← run() + parseOrThrow() + withAudit()
        │
  application                        4,842줄   ← 서비스. 여기서 assertCan() 권한 검사
        │
  repositories                       8,498줄   ← DEMO(파일) / Supabase 두 구현
        │
  domain                             4,345줄   ← 타입과 규칙. 의존성 0
```

**이 경계는 ESLint 가 강제합니다.**

- `src/domain/` 은 아무것도 import 하지 않습니다 (순수 규칙, 단위 테스트 대상).
- 화면에서 `repositories` 를 직접 import 하면 **lint 가 실패합니다.** 권한 검사와
  감사 로그를 우회하는 경로를 원천 차단하기 위해서입니다.

### 4-3. 주요 기능

| | 기능 | 구현 위치 |
|---|---|---|
| ① | **AI 도구 공유 생태계** — 등록·평가·개선 요청·소통 | 플랫폼 전체 |
| ② | **중복 자동화 탐지** — 어휘 필터 + LLM 2단계 | `adapters/ai/live/duplicate-detection.ts` |
| ③ | **위험도 자동 평가** — 14항목 제안 + 사람 확정 | `adapters/ai/live/risk-assessment.ts` |
| ④ | **멀티 LLM 품질검증** — 모델 둘 교차, 불일치 노출 | `adapters/ai/live/quality-review.ts` |

### 4-4. 핵심 기술과 설계 판단

**권한 모델 — 역할 하나가 아니라 축 셋**

| 축 | 값 | 의미 |
|---|---|---|
| 계정 유형 | 이용자 / 관리자 | |
| 관리 권한 | **6종** (검토·사용자·카테고리·도구·공지·감사) | **관리자라고 다 되는 것이 아니다** |
| 학내 신분 | 학생·교직원·교수 | **권한이 아니다.** 추천 대상 표시에만 쓴다 |

판단 기준은 둘입니다 — **내가 만든 것인가**(소유권), **그 권한을 받았는가**.
**관리 권한으로 소유권을 넘지 않습니다.** 관리자도 남의 도구 내용이나 남이 쓴 평가는
고칠 수 없습니다.

**상태 기계** — 도구 상태 9개, 전환 규칙 **11개**를 표 하나에 모았습니다. 화면에서
버튼을 감췄는지와 무관하게 **모든 상태 변경이 이 표를 통과**합니다. 위험도 '매우 높음'인
도구는 시범운영·정식 승인으로 갈 수 없습니다.

**모델로 나가는 내용은 허용 목록만 통과** — `adapters/ai/live/redact.ts` 한 곳을
반드시 거칩니다. 허용된 필드는 도구 이름·소개·문제·기능·업무 흐름·입출력·자동화 수준·
분류·태그·데이터 등급·외부 전송 여부 **15개**뿐입니다. 도메인 타입에 필드가 새로 생겨도
여기 적지 않으면 나가지 않습니다. **등록자·검토자 이름, 이메일, 부서는 나가지 않습니다.**

**한국어 처리** — 조사를 `은(는)` 처럼 쓰지 않습니다. 받침을 보고 고르는 `josa()` 함수를
씁니다. 날짜는 공용 포맷 함수를 거칩니다.

**접근성** — 상태를 **텍스트 + 아이콘 + 색 3중**으로 표시합니다. 색만으로 구분하지
않습니다. 펼쳐보기는 `<details>` 를 써서 접힌 내용도 Ctrl+F 로 찾힙니다.

### 4-5. 시범 적용 결과

**AI 분석을 실제로 돌렸습니다.** 시늉이 아니라 교내 AI 게이트웨이를 경유한 실제 호출입니다.

## 5. 기타 (품질 및 AI 활용 역량)

### 5-1. 사용자 경험 — 세 번의 리뷰를 받아 고쳤습니다

만들어 놓고 끝내지 않고, 실제 사용자가 화면을 하나씩 눌러 보며 남긴 지적을 **네 차례**
(2026-08-26 ~ 08-29) 받아 반영했습니다. 리뷰 기록은 `docs/REVIEW-2026-08-25.md`, `docs/REVIEW-2026-08-26.md` 에
그대로 남아 있습니다. 대표적인 지적과 대응입니다.

| 지적 | 무엇이 문제였나 | 어떻게 고쳤나 |
|---|---|---|
| "수요 등록에서 같은 걸 여러 번 물어본다" | 빈 칸에 자기 업무를 설명하라는 요구 자체가 어려운 숙제 | 다섯 단계를 **전부 버튼**으로. 서술형은 마지막 한 칸만, 그것도 선택 |
| "다운받거나 실행할 버튼이 없음" | 도구를 모으기만 하고 쓸 방법이 없었음 | 상세 화면 맨 위에 **「이 도구 쓰기」** 추가. 신청 시 접근 경로를 필수로 |
| "내가 올린 도구를 수정할 수 없음" | 오타 하나 고치려면 검토자에게 부탁해야 했음 | **신청 취소하고 수정**, 승인 후에는 **새 버전** 경로 추가 |
| "정보가 너무 많아 눈에 안 들어옴" | 검토 화면에 카드 6장이 같은 무게로 쌓여 있었음 | 접어 두기 + **다섯 단계 마법사**로 재구성 |
| "'검토 시작'이 안 됨" | 입력 검증과 상태 규칙이 서로 다른 말을 하고 있었음 | 규칙을 한 곳으로 모으고, 전환 표 전체를 검사하는 테스트 추가 |
| "알림을 눌러도 아무 일이 없음" | 읽음 표시가 남아 링크가 동작하지 않는 것처럼 보였음 | 클릭 시 읽음 처리 + 팝오버 닫기 |

**오류 메시지 원칙** — "무엇이 잘못됐는지 + 어떻게 고치는지" 두 부분으로 씁니다.
개발자 용어를 쓰지 않습니다. 화면에 그대로 나가는 문장이기 때문입니다.

### 5-2. AI 활용 역량

**(가) 제품 안에서의 생성형 AI 활용**

단순 호출이 아니라 **역할을 나누고, 한계를 설계에 반영**했습니다.

| 활용 | 수준 |
|---|---|
| 2단계 파이프라인 | 어휘 필터로 후보를 좁힌 뒤 LLM 1회 — O(N²) 회피 |
| 멀티 모델 교차 검증 | 모델 둘의 판정 불일치를 **감추지 않고 노출** |
| 구조화 출력 | 판정·점수·근거·권고를 스키마로 받아 화면에 그대로 매핑 |
| 사전 실행 / 결과 저장 | 화면에서 모델을 부르지 않아 **재현성·응답속도·비용** 확보 |
| 실패 대비 | 초안 다듬기 실패 시 규칙 기반 초안으로 끝까지 진행 |
| 데이터 최소화 | 허용 목록 15개 필드만 전송. 사람 이름·이메일·부서 제외 |
| 출처 표시 | 어느 모델이 언제 분석했는지 화면에 명시. `아직 사람이 확인하지 않음` 배지 |
| 비용 집계 | 호출마다 토큰·비용 집계 (`--dry-run` 으로 사전 추정 가능) |

**가장 중요한 판단은 "AI 에게 시키지 않은 것"입니다.**
순위 계산, 위험 체크리스트 채우기, 최종 승인 — 셋 다 기술적으로 가능하지만
**의도적으로 사람에게 남겼습니다.** 설명할 수 없는 판단을 자동화하지 않는 것이
행정 시스템에서는 기능을 하나 더 넣는 것보다 중요합니다.

**(나) 개발 과정에서의 생성형 AI 활용**

이 플랫폼은 **Claude Code(생성형 AI 코딩 에이전트)와 함께 개발**했습니다.
사람이 요구사항·설계 판단·사용자 리뷰를 맡고, AI 가 구현·테스트·문서화를 맡는 방식입니다.

- **설계 결정을 문서로 고정** — `docs/DECISIONS.md`, `CLAUDE.md` 에 "하지 말 것"을
  명시해 AI 가 되돌리지 못하게 했습니다. (예: 도메인 계층 의존성 0 유지, AI 제안으로
  체크리스트 자동 채우기 금지)
- **규칙을 lint 로 강제** — 지침을 글로만 두지 않고 ESLint 규칙으로 만들어, 어길 경우
  빌드가 실패하게 했습니다.
- **테스트 469개** 로 회귀를 잡았습니다. 실제로 이 방식이 승인 경로 전체가 막혀 있던
  결함을 찾아냈습니다.
- **네 차례 사용자 리뷰**(2026-08-26 ~ 08-29)를 문서로 받아 단계적으로 반영했습니다.

36,706줄 규모를 짧은 기간에 만들 수 있었던 것은 AI 활용 덕분이지만, **무엇을 만들지
않을지 정하는 일**은 사람이 했습니다. 이 보고서에 "아직 안 된 것"을 따로 적은 것도
같은 이유입니다.

### 5-3. 품질 지표

```
lint       통과 (오류 0, 경고 0)
typecheck  통과 (strict + noUncheckedIndexedAccess)
test       469개 통과 (28개 파일)
build      통과
```

- **TypeScript strict** 에 더해 `noUncheckedIndexedAccess` 를 켰습니다. 배열 접근이
  `undefined` 일 가능성을 컴파일러가 강제로 확인하게 합니다.
- **계층 경계를 lint 로 강제** — 사람의 주의력에 의존하지 않습니다.
- **통합 테스트는 실제 권한 로직을 사용**합니다. 세션만 갈아 끼우고 권한 판단은
  진짜를 씁니다.
