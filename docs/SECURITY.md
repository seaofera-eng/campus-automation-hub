## 권한 검사가 이중인 이유

화면에서 버튼을 감추는 것은 **보안 경계가 아닙니다.** 주소를 직접 입력하거나
요청을 만들어 보내면 우회됩니다. 그래서 세 겹으로 막습니다.

1. **UI** — `canProfile()` 로 버튼을 감춥니다. 사용자 편의입니다.
2. **서버 액션 / 페이지 로더** — `assertCan()` 이 던집니다. 여기가 실제 경계입니다.
3. **RLS** (Supabase 모드) — 애플리케이션에 버그가 있어도 DB 가 막습니다.

E2E 테스트가 이것을 확인합니다: 수요자로 로그인해 `/reviews`, `/admin`, `/tools/new`
주소를 직접 열면 모두 404 가 돌아옵니다.

## 권한 없음을 404 로 보여주는 이유

`src/lib/auth/page-guard.ts` 는 `FORBIDDEN` 과 `NOT_FOUND` 를 **똑같이 404** 로
처리합니다.

"권한이 없습니다"라고 알려 주면 그 항목이 **존재한다는 사실**이 새어 나갑니다.
목록에서 걸러진 도구의 주소를 하나씩 찍어 보며 존재 여부를 확인하는 것을 막습니다.

## 감사 로그에 무엇을 남기고 무엇을 남기지 않는가

**남긴다**: 누가 · 언제 · 무슨 작업을 · 어떤 대상에 · 어떤 **필드**를 바꿨는지 ·
성공/실패 · IP · User-Agent

**남기지 않는다**: 바뀐 **값** 자체

개인정보나 상담 내용이 로그로 새어 나가면 안 되기 때문입니다. 값이 필요하면
원본 테이블을 보면 됩니다. 통합 테스트가 이것을 검증합니다 — 사용자 직위를
"비밀 직위명"으로 바꾼 뒤 로그 전체를 문자열로 훑어도 그 값이 없어야 합니다.

예외적으로 **역할 변경 사유**는 요약에 넣습니다. 개인정보가 아니라 권한 변경의
근거이고, 그것을 남기는 것이 감사 기록의 목적이기 때문입니다.

## 관리자 자기 자신에 대한 제약

- **자기 역할은 스스로 바꿀 수 없다** — 실수로 자기 권한을 낮추는 것과, 권한
  상승을 혼자 처리하는 것을 함께 막습니다. RLS 의 `user_roles_admin_write` 정책도
  `user_id <> auth.uid()` 조건을 겁니다.
- **자기 계정은 비활성화할 수 없다** — 즉시 로그아웃되어 되돌릴 수 없습니다.

## DEMO 모드 세션

DEMO 모드에는 비밀번호가 없습니다. 그래도 쿠키에 **HMAC-SHA256 서명**을 붙입니다.
서명이 없으면 브라우저에서 쿠키를 고쳐 다른 사용자로 위장할 수 있기 때문입니다.

- `HttpOnly`, `SameSite=Lax`, 운영 환경에서는 `Secure`
- 만료 8시간
- 서명 불일치·형식 오류·만료는 전부 `null` 로 처리하고 **왜 실패했는지 알려주지 않음**

## ⚠️ 아직 검증되지 않은 것

**Supabase RLS 정책은 실제 데이터베이스에서 실행된 적이 없습니다.**

DEMO 모드 우선으로 진행했기 때문에 `supabase/migrations/` 의 SQL 은 작성만 되어
있고 적용되지 않았습니다. 처음 연결할 때 다음을 반드시 확인해야 합니다.

- [ ] 마이그레이션 0001~0012 가 순서대로 적용되는가
- [ ] 각 역할로 로그인해 다른 부서의 `DRAFT` 도구가 조회되지 않는가
- [ ] `audit_logs` 에 일반 사용자가 `INSERT` 할 수 없는가 (insert 정책 없음)
- [ ] `tool_status_history` 를 `UPDATE`·`DELETE` 하면 트리거가 거부하는가
- [ ] 관리자가 자기 `user_roles` 행을 수정하려 하면 정책이 막는가
- [ ] 첨부파일 버킷이 **비공개**이고 서명 URL 로만 열리는가

애플리케이션 레벨 권한 검사가 1차 방어선이고 단위 테스트로 덮여 있으므로,
RLS 가 미검증이어도 기능은 동작합니다. 다만 **RLS 를 두 번째 방어선으로 믿으려면
위 확인이 끝나야 합니다.**
