## 0. 지금 어디에 서 있는가

출품 설명서의 **주요 기능 4가지**를 지금 상태와 맞춰 보면 이렇습니다.

| 주요 기능 | 지금 | 남은 일 |
|---|---|---|
| ① AI 도구 공유 — 등록·평가·소통 생태계 | ✅ **완성** | 없음 |
| ② 중복 자동화 탐지 | ❌ Noop 만 | **전부** |
| ③ 위험도 자동 평가 | ⚠️ 사람이 하는 체크리스트 14항목만 | 자동 제안 계층 |
| ④ 멀티 LLM 품질검증 | ❌ Noop 만 | **전부** |

요구사항 4가지는 이렇습니다.

| 요구사항 | 지금 | 남은 일 |
|---|---|---|
| 평가 + 개선 요구 + **순위 매겨 우선순위 추천** | 평가·개선 ✅ / 순위 ❌ | 순위 계산 + 추천 |
| 수요 등록 → 매칭 / 개발 → 평가 | 수동 매칭만 | **자동 매칭 후보 제시** |
| 기존 도구 참고해 업데이트·**통합 표준화** | ❌ | 신규 |
| 개발자 토큰 | ✅ **완성** | 없음 |

**한 줄 요약: 플랫폼(생태계)은 다 됐고, "AI 관제"라고 부를 수 있게 하는 네 기능이 비어 있습니다.**

## 1. 이 로드맵을 관통하는 원칙

지금까지 지켜 온 규칙이 있습니다. **AI를 붙인다고 이걸 깨면 안 됩니다.**

> 가짜 AI 결과를 만들지 않는다. 점수·유사도·판정을 지어내지 않는다.

지금까지는 "그러니 아무것도 안 만든다"로 지켜 왔습니다. 이제부터는 다르게 지킵니다.

### ① 계산한 것과 판단한 것을 화면에서 구분한다

- **기계적 유사도** (문자열 비교) — 결정적이고 재현 가능. "유사도"라고만 부릅니다.
- **모델 판단** (LLM) — 반드시 **근거 문장**을 함께 저장하고 보여 줍니다.

숫자만 덩그러니 보여주는 화면은 만들지 않습니다.

### ② AI는 제안하고 사람이 확정한다

이미 `RiskAssessmentResult.suggestedLevel` 에 "AI가 제안한 등급. 최종 확정은 항상 사람이 한다"고 적혀 있습니다. 이 구조를 전부에 적용합니다.

- 중복 탐지 → 검토자에게 **후보**를 보여줌. 판정은 사람이.
- 위험도 → **제안 등급**. 체크리스트는 여전히 사람이.
- 멀티 LLM → 모델끼리 의견이 갈리면 `NEEDS_HUMAN_REVIEW`.

### ③ 모델이 없어도 화면이 죽지 않는다

API 키가 없거나 호출이 실패하면 **지금의 Noop 동작으로 되돌아갑니다.** 심사 시연 중 네트워크가 끊겨도 플랫폼은 그대로 돌아가야 합니다.

### ④ 이미 만들어 둔 계약을 쓴다

`src/adapters/ai/types.ts` 에 6개 서비스 인터페이스가 **전부 정의돼 있습니다.**
`supabase/migrations/0009` 에 10개 테이블이 **전부 예약돼 있습니다.**

```
duplicate_detection_runs   duplicate_candidates    risk_assessments
llm_review_runs            llm_review_results      ranking_snapshots
reward_rules               developer_contributions reward_ledgers
monthly_reward_snapshots
```

**새로 설계할 것이 거의 없습니다.** Noop 자리에 살아 있는 구현을 넣는 일입니다.

## 2. 기술 선택

### 모델

TypeScript 프로젝트이므로 `@anthropic-ai/sdk` 를 씁니다.

| 쓰임 | 모델 | 가격 (입력/출력, 1M당) | 이유 |
|---|---|---|---|
| 중복 판정 · 위험 제안 · 매칭 설명 | `claude-opus-5` | $5 / $25 | 근거를 조리 있게 쓰는 일이라 품질이 중요 |
| 대량 1차 분류 (선택) | `claude-haiku-4-5` | $1 / $5 | 후보 걸러내기처럼 단순·대량인 작업 |
| 멀티 LLM 교차 검증 | `claude-opus-5` + `claude-sonnet-5` | — | **서로 다른 모델**이어야 교차 검증의 뜻이 생김 |

> 멀티 LLM은 "여러 번 부르기"가 아니라 **다른 모델에게 다른 관점으로 묻는 것**입니다.
> 사실성은 Opus, 규정·보안은 Sonnet — 이렇게 나누면 의견이 갈리는 지점이 실제로 드러납니다.

### 임베딩이 없다는 문제

Anthropic API에는 임베딩 엔드포인트가 없습니다. 도구가 N개일 때 모든 쌍을 LLM으로 비교하면 **O(N²)** 호출이라 비용이 감당되지 않습니다.

**2단계 방식으로 풉니다.**

```
1단계 — 기계적 유사도 (LLM 호출 없음, 즉시, 무료)
        이름·한 줄 소개·주요 기능·태그를 문자 3-gram + 자카드 유사도로 비교
        상위 5개만 통과시킴
              ↓
2단계 — 모델 판단 (통과한 5개만 LLM 호출)
        "이 둘이 같은 일을 하는가"를 근거와 함께 판정
```

도구 100개여도 등록 1건당 LLM 호출은 **최대 5회**입니다.

이 방식은 정직하기도 합니다. 1단계 점수는 "글자가 얼마나 겹치는지"이고 화면에도 그렇게 씁니다. 의미를 이해한 척하지 않습니다.

### 비용 추정 (데모 규모)

도구 100개 · 수요 50건 기준, 한 번 전체 분석:

| 작업 | 호출 수 | 대략 비용 |
|---|---|---|
| 중복 탐지 (도구당 5쌍) | 500 | $2~4 |
| 위험도 제안 (도구당 1) | 100 | $1~2 |
| 수요 매칭 (수요당 5) | 250 | $1~2 |
| 멀티 LLM (도구당 3관점) | 300 | $2~4 |

**전체 $6~12 수준.** 배치 API를 쓰면 절반입니다. 심사용 시연에는 충분합니다.

## 3. 단계별 계획

### 6단계 — 살아 있는 어댑터 뼈대 🔜

> **먼저 배관을 깔고, 기능은 그 위에 하나씩 올립니다.**

- [ ] `@anthropic-ai/sdk` 추가, `ANTHROPIC_API_KEY` 환경변수
- [ ] `src/adapters/ai/live/client.ts` — 클라이언트 하나. 재시도·타임아웃·비용 로깅
- [ ] `src/adapters/ai/index.ts` 에서 **키가 있으면 live, 없으면 noop** 선택
- [ ] 모든 live 구현은 실패 시 **noop 결과로 떨어짐** (원칙 ③)
- [ ] `ai_call_logs` 테이블 — 어떤 기능이 언제 얼마를 썼는지. 심사 때 보여줄 수 있는 자료
- [ ] 구조화 출력(`output_config.format`)으로 응답을 스키마에 맞춤. 파싱 실패를 없앰

**끝나면**: 아무 기능도 안 바뀌지만, 그 위에 뭐든 올릴 수 있는 상태.

### 7단계 — ② 중복 자동화 탐지 🔜

가장 먼저 하는 이유: **주요 기능 중 완전히 비어 있는 것 중 시연 효과가 가장 큽니다.** "같은 걸 또 만들고 있다"를 화면으로 보여주는 게 이 플랫폼의 존재 이유입니다.

- [ ] `src/domain/similarity/` — 3-gram 자카드 유사도. **순수 함수, 단위 테스트**
- [ ] `DuplicateDetectionService` live 구현
  - `findCandidates()` — 기계적 유사도로 상위 5개
  - `compareTools()` — LLM이 판정 + 근거
- [ ] 도구 **등록 신청 시 자동 실행** (`after()` 로 응답 뒤에)
- [ ] 검토 화면에 "비슷한 도구 N건" 카드. 각 후보마다 **왜 비슷한지 한 문장**
- [ ] 도구 상세에 "이 도구와 비슷한 것" 표시
- [ ] 결과를 `duplicate_detection_runs` / `duplicate_candidates` 에 저장

**화면에 이렇게 나옵니다**

```
⚠ 비슷한 도구가 2건 있습니다

[예시] AI 회의록 정리 도구          글자 유사도 72%
  판정: 거의 같은 일을 합니다
  근거: 둘 다 녹취를 요약해 담당자별 할 일로 나눕니다. 입력(녹취 파일)과
        결과물(과업 표)이 같습니다. 다른 점은 이 도구가 캘린더 등록을
        추가로 한다는 것뿐입니다.
  → 새로 만들기보다 기존 도구에 캘린더 기능을 개선 요청하는 편이 낫습니다.
```

마지막 줄이 **요구사항 3번("기존 도구를 참고해 업데이트")** 으로 이어집니다.

### 8단계 — ③ 위험도 자동 평가 🔜

지금은 사람이 14항목을 체크합니다. **그걸 없애지 않습니다.** 앞에 제안 계층을 붙입니다.

- [ ] `RiskAssessmentService` live 구현
  - 입력: 데이터 분류, 외부 전송 여부, 자동화 수준, 기능 설명, 업무 흐름
  - 출력: 제안 등급 + **14항목 각각에 대한 해당 여부와 이유** + 필요한 통제 방안
- [ ] 검토 화면에서 체크리스트에 **AI 제안을 미리 표시**. 검토자는 확인·수정만
- [ ] 제안과 사람 판정이 **다르면 그 사실을 남김** (나중에 정확도를 말할 수 있는 근거)
- [ ] CRITICAL 제안이면 눈에 띄게 경고
- [ ] `risk_assessments` 에 저장

**지켜야 할 것**: 저장되는 최종 등급은 **언제나 사람이 고른 것**입니다. AI 제안은 별도 컬럼입니다.

### 9단계 — 자동 매칭 + 순위·추천 🔜

요구사항 1번과 2번을 함께 처리합니다. 둘 다 "무엇을 먼저 보여줄까"라는 같은 문제입니다.

**자동 매칭**

- [ ] `DemandMatchingService` live 구현 — 중복 탐지와 같은 2단계 방식
- [ ] 수요 상세에 "이 수요에 맞을 것 같은 도구" 후보 + 근거
- [ ] **연결은 여전히 사람이 확정** (기존 규칙 유지)
- [ ] 랜딩의 "추천 도구"를 신분 기반에서 **매칭 기반**으로 승격

**순위**

- [ ] `RankingService` live 구현. 가중치는 `DEFAULT_RANKING_WEIGHTS` 그대로
  ```
  평가 품질 30% · 채택도 20% · 절감 시간 15% · 안전성 15%
  안정성 10% · 유지보수 5% · 확산도 5%
  ```
- [ ] **베이지안 보정** — 평가 1건에 5점 받은 신규 도구가 1등이 되면 안 됩니다.
      `DEFAULT_RANKING_GUARDS.bayesianPriorWeight` 를 씁니다
- [ ] `SUSPENDED` / `RETIRED` 는 순위에서 제외
- [ ] 순위 계산 근거를 **펼쳐 볼 수 있게** — 어느 항목에서 몇 점인지
- [ ] `ranking_snapshots` 에 저장. 시점별 변화를 볼 수 있음

> **순위는 AI가 아닙니다.** 정해진 가중치로 계산하는 것이고, 화면에도 그렇게 씁니다.
> 계산식을 감추면 "왜 저게 1등이냐"에 답할 수 없습니다.

### 10단계 — ④ 멀티 LLM 품질검증 🔜

가장 나중에 하는 이유: 앞의 것들이 없으면 검증할 대상이 없습니다.

- [ ] 도구에 **테스트 케이스** 등록 기능 (입력 예시 + 기대 결과)
- [ ] `MultiLlmReviewService` live 구현 — 세 관점을 **다른 모델에**
  | 관점 | 모델 | 묻는 것 |
  |---|---|---|
  | 사실성 | `claude-opus-5` | 결과가 근거와 맞는가, 지어낸 내용이 있는가 |
  | 규정 | `claude-sonnet-5` | 학칙·개인정보 규정에 어긋나는 안내가 있는가 |
  | 보안 | `claude-sonnet-5` | 민감정보가 결과에 새어 나오는가 |
- [ ] **의견이 갈리면 `NEEDS_HUMAN_REVIEW`** — 이게 이 기능의 핵심입니다.
      셋 다 통과해야 PASS. 하나라도 갈리면 사람에게
- [ ] 검토 화면에 세 관점의 판정과 **각각의 지적 사항**
- [ ] `llm_review_runs` / `llm_review_results` 에 저장

**화면에 이렇게 나옵니다**

```
멀티 LLM 품질검증 — 사람 확인 필요 ⚠

사실성  Opus 5     통과    지어낸 조항 없음. 근거 링크가 모두 실재함
규정    Sonnet 5   실패 ⚠  "성적 정정은 담당 교수 재량"이라 답했으나
                          학칙 32조는 학과장 승인을 요구함
보안    Sonnet 5   통과    답변에 학번·이름이 포함되지 않음

→ 규정 관점에서 문제가 제기되어 검토자 확인이 필요합니다.
```

### 11단계 — 통합 표준화 (요구사항 3번) 🔜

가장 뒤에 두는 이유: **7단계(중복 탐지)의 결과가 쌓여야 할 수 있는 일입니다.**

- [ ] 중복 판정이 누적된 도구들을 **묶음으로 제시** ("이 3개는 같은 일을 합니다")
- [ ] 묶음에서 **기능 비교 표**를 자동 생성 — 어느 도구에 어떤 기능이 있는지
- [ ] "통합 제안" — 어느 것을 기준으로 삼고 무엇을 흡수할지 LLM이 초안
- [ ] 제안을 **개선 요청으로 전환**하는 버튼 (기존 개선 요청 흐름 재사용)
- [ ] 도구 상세에 "이 도구를 참고한 도구" / "이 도구가 참고한 도구" 연결

## 4. 순서를 이렇게 정한 이유

```
6단계 배관        ← 이게 없으면 나머지를 못 올림
  ↓
7단계 중복 탐지   ← 시연 효과 최대. 플랫폼 존재 이유를 보여줌
  ↓
8단계 위험도      ← 이미 있는 체크리스트에 얹기만 하면 됨. 비용 대비 성과 큼
  ↓
9단계 매칭·순위   ← 요구사항 1·2를 함께. 데이터가 쌓인 뒤라야 의미 있음
  ↓
10단계 멀티 LLM   ← 검증할 대상(테스트 케이스)이 먼저 있어야 함
  ↓
11단계 통합 표준화 ← 7단계 결과가 누적돼야 가능
```

**시간이 부족하면 6·7·8단계까지가 최소선입니다.** 그 시점에 주요 기능 4개 중 3개가 살아 있고, 나머지 하나(멀티 LLM)는 "설계와 인터페이스는 있고 3단계 예정"으로 정직하게 설명할 수 있습니다.

## 5. 심사에서 물어볼 만한 것 — 미리 준비할 답

| 질문 | 답할 수 있게 만들어 둘 것 |
|---|---|
| "이 유사도 72%는 어떻게 나온 숫자인가?" | 계산식을 화면에 노출. 3-gram 자카드라고 명시 |
| "AI가 틀리면?" | 제안과 사람 판정이 다른 경우를 저장 → 통계로 보여줄 수 있음 |
| "모델이 지어낸 것 아닌가?" | 모든 판단에 근거 문장 필수. 구조화 출력으로 형식 강제 |
| "비용이 얼마나 드나?" | `ai_call_logs` 로 기능별 실제 비용 집계 |
| "개인정보가 외부 모델로 가지 않나?" | **중요** — 아래 참고 |

### 개인정보 처리 — 반드시 짚고 갈 것

LLM에 보내는 내용을 **도구 메타데이터로만 제한**해야 합니다.

- ✅ 보내도 되는 것: 도구 이름, 소개, 기능 목록, 업무 흐름 설명, 데이터 분류 **이름**
- ❌ 보내면 안 되는 것: 실제 처리 데이터, 첨부파일 내용, 평가 원문, 문의 원문

이 경계를 **코드에 못박고 테스트로 지켜야 합니다.** 학내 플랫폼이라 심사에서 반드시 나올 질문이고, "안 보냅니다"를 코드로 보여줄 수 있어야 합니다.

- [ ] `src/adapters/ai/live/redact.ts` — LLM에 보낼 payload를 만드는 **유일한 통로**
- [ ] 허용 목록 방식. 새 필드는 명시적으로 추가해야 나감
- [ ] 단위 테스트: 개인정보가 섞인 입력을 넣고 payload에 안 들어가는지 확인

## 6. 아직 정하지 않은 것

진행 전에 답이 필요합니다.

1. **API 키와 예산** — Anthropic 콘솔 계정이 있으신가요? 없으면 6단계에서 막힙니다.
2. **테스트 케이스를 누가 넣나** — 멀티 LLM 검증은 "이 입력에 이런 결과가 나와야 한다"가 있어야 돌아갑니다. 도구 등록자가 넣게 할까요, 검토자가 넣게 할까요?
3. **출품 마감일** — 어디까지 갈지가 여기서 정해집니다.
4. **시연 방식** — 실시간으로 API를 부를지, 미리 돌려 둔 결과를 보여줄지. 네트워크가 불안하면 후자가 안전합니다.
