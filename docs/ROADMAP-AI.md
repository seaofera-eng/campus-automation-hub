## 1. 이 로드맵을 관통하는 원칙

지금까지 지켜 온 규칙이 있습니다. **AI를 붙인다고 이걸 깨면 안 됩니다.**

> 가짜 AI 결과를 만들지 않는다. 점수·유사도·판정을 지어내지 않는다.

지금까지는 "그러니 아무것도 안 만든다"로 지켜 왔습니다. 이제부터는 다르게 지킵니다.

### ① 계산한 것과 판단한 것을 화면에서 구분한다

- **기계적 유사도** (문자열 비교) — 결정적이고 재현 가능. "유사도"라고만 부릅니다.
- **모델 판단** (LLM) — 반드시 **근거 문장**을 함께 저장하고 보여 줍니다.

숫자만 덩그러니 보여주는 화면은 만들지 않습니다.

### ② AI는 제안하고 사람이 확정한다

이미 `RiskAssessmentResult.suggestedLevel` 에 "AI가 제안한 등급. 최종 확정은 항상 사람이 한다"고 적혀 있습니다. 이 구조를 전부에 적용합니다.

- 중복 탐지 → 검토자에게 **후보**를 보여줌. 판정은 사람이.
- 위험도 → **제안 등급**. 체크리스트는 여전히 사람이.
- 멀티 LLM → 모델끼리 의견이 갈리면 `NEEDS_HUMAN_REVIEW`.

### ③ 모델이 없어도 화면이 죽지 않는다

API 키가 없거나 호출이 실패하면 **지금의 Noop 동작으로 되돌아갑니다.** 심사 시연 중 네트워크가 끊겨도 플랫폼은 그대로 돌아가야 합니다.

### ④ 예약해 둔 계약은 참고만 한다

`0009` 에 10개 테이블을 예약해 두었지만, 실제로 만들고 보니 모양이 달랐습니다.
그때는 "실행 이력"을 남기는 구조로 잡아 두었는데, 필요한 것은 **도구 버전 하나당
최신 분석 하나**였습니다. 버전이 바뀌면 새 행이 생기므로 이력은 버전을 따라 남습니다.

`0017` 에서 다음 다섯을 대체했습니다 (0009 는 한 번도 적용된 적이 없어 버릴
데이터가 없습니다):

```
duplicate_detection_runs + duplicate_candidates  →  duplicate_analyses
risk_assessments                                 →  risk_analyses
llm_review_runs + llm_review_results             →  quality_reviews
(신규)                                            →  demand_analyses
```

`src/adapters/ai/types.ts` 의 6개 서비스 인터페이스도 지웠습니다. 한 곳에서도
쓰이지 않았고, 실제 구현의 모양과 맞지 않았습니다. 순위 가중치만 `domain/ranking/`
으로 옮겨 살렸습니다.

**교훈**: 쓰기 전에 잡아 둔 인터페이스는 참고 자료지 계약이 아닙니다.

## 2. 기술 선택

### 모델

TypeScript 프로젝트이므로 `@anthropic-ai/sdk` 를 씁니다.

| 쓰임 | 모델 | 가격 (입력/출력, 1M당) | 이유 |
|---|---|---|---|
| 중복 판정 · 위험 제안 · 매칭 설명 | `claude-opus-5` | $5 / $25 | 근거를 조리 있게 쓰는 일이라 품질이 중요 |
| 대량 1차 분류 (선택) | `claude-haiku-4-5` | $1 / $5 | 후보 걸러내기처럼 단순·대량인 작업 |
| 멀티 LLM 교차 검증 | `claude-opus-5` + `claude-sonnet-5` | — | **서로 다른 모델**이어야 교차 검증의 뜻이 생김 |

> 멀티 LLM은 "여러 번 부르기"가 아니라 **다른 모델에게 다른 관점으로 묻는 것**입니다.
> 사실성은 Opus, 규정·보안은 Sonnet — 이렇게 나누면 의견이 갈리는 지점이 실제로 드러납니다.

### 임베딩이 없다는 문제

Anthropic API에는 임베딩 엔드포인트가 없습니다. 도구가 N개일 때 모든 쌍을 LLM으로 비교하면 **O(N²)** 호출이라 비용이 감당되지 않습니다.

**2단계 방식으로 풉니다.**

```
1단계 — 기계적 유사도 (LLM 호출 없음, 즉시, 무료)
        이름·한 줄 소개·주요 기능·태그를 문자 3-gram + 자카드 유사도로 비교
        상위 5개만 통과시킴
              ↓
2단계 — 모델 판단 (통과한 5개만 LLM 호출)
        "이 둘이 같은 일을 하는가"를 근거와 함께 판정
```

도구 100개여도 등록 1건당 LLM 호출은 **최대 5회**입니다.

이 방식은 정직하기도 합니다. 1단계 점수는 "글자가 얼마나 겹치는지"이고 화면에도 그렇게 씁니다. 의미를 이해한 척하지 않습니다.

### 비용 추정 (데모 규모)

도구 100개 · 수요 50건 기준, 한 번 전체 분석:

| 작업 | 호출 수 | 대략 비용 |
|---|---|---|
| 중복 탐지 (도구당 5쌍) | 500 | $2~4 |
| 위험도 제안 (도구당 1) | 100 | $1~2 |
| 수요 매칭 (수요당 5) | 250 | $1~2 |
| 멀티 LLM (도구당 3관점) | 300 | $2~4 |

**전체 $6~12 수준.** 배치 API를 쓰면 절반입니다. 심사용 시연에는 충분합니다.

**바뀐 설계**: `ai_call_logs` 테이블 대신 `drainUsage()` 로 실행 단위 집계를 합니다.
분석이 앱이 아니라 스크립트에서 도니 DB 테이블이 필요 없습니다.

**바뀐 설계**: "키가 있으면 live, 없으면 noop" 대신 **분석은 스크립트가 미리 돌리고
앱은 저장된 것만 읽습니다.** 이유는 셋입니다 — 페이지를 열 때마다 부르면 느리고
비싸고, 새로 고칠 때마다 판단이 달라지면 검토 자료로 못 쓰고, 시연 자리에서 키와
망에 기대고 싶지 않습니다.

### 7단계 — ② 중복 자동화 탐지 ✅

- [x] `src/domain/similarity/` — 글자 3-gram 자카드. 순수 함수, 단위 테스트 17개
- [x] 두 단계 비교 — 글자로 후보 5개를 좁히고 모델을 **한 번만** 부릅니다
- [x] 판정 + 겹치는 점 + **다른 점** + 처리 제안 + 근거 한 문단
- [x] 검토 화면 · 도구 상세에 카드
- [x] `duplicate_analyses` 에 저장 (0017)

**처리 제안 4종**이 요구사항 3번("기존 도구를 참고해 업데이트")으로 이어집니다:
기존 도구로 충분함 / 기존 도구에 합치기 / 역할을 나눠 둘 다 두기 / 그대로 진행.

### 8단계 — ③ 위험도 자동 평가 ✅

- [x] 검토자가 쓰는 것과 **같은 14개 항목**에 대한 의견 + 근거 + 등록 내용 인용
- [x] 검토 화면에서 체크리스트 **위에** 표시. 체크박스를 자동으로 채우지 않습니다
- [x] 제안과 검토자 판단이 갈린 항목을 세어 보여 줍니다
- [x] 근거를 못 대면 '해당 없음'으로 내립니다
- [x] CRITICAL 후보 항목이 걸렸는데 등급이 낮으면 등급을 올립니다 (내리지는 않음)
- [x] `risk_analyses` 에 저장 (0017)

**체크박스를 자동으로 채우지 않은 이유**: 채워 두면 검토자가 그대로 넘깁니다.
그러면 검토가 없는 것과 같습니다.

**자동 매칭**

- [x] 중복 탐지와 같은 두 단계 방식
- [x] 세 갈래 판정 — 그대로 됨 / 조금 고치면 됨 / 새로 만들어야 함
- [x] **못 하는 기능 목록**이 그대로 개발 범위가 됩니다
- [x] 연결 확정은 여전히 사람이 합니다
- [x] `demand_analyses` 에 저장 (0017)

**순위** — `/ranking`

- [x] `src/domain/ranking/` 순수 계산, 단위 테스트 22개
- [x] **가중치를 다시 잡았습니다.** 예전 7종은 근거 데이터가 없었습니다 —
      부서는 0014 에서 제거됐고, 평가는 종합 점수 하나로 단순화됐고, 절감 시간

      만족도 35% · 실제 쓰임 25% · 안정성 15% · 안전 15% · 관리 상태 10%

- [x] 베이지안 보정 (기존 `bayesianAdjustedScore` 재사용)
- [x] `SUSPENDED`/`RETIRED`·CRITICAL 등급은 제외하되 **사유와 함께 보여 줍니다**
- [x] 평가가 모자란 도구는 순위표에 '표본 부족' 표시를 달고 그대로 두고,
      추천에서만 뺍니다. 빼 버리면 새로 만든 좋은 도구가 영원히 안 보입니다
- [x] 축별 점수를 막대로 펼치고 가중치를 화면에 그대로 적습니다

**바뀐 설계**: `ranking_snapshots` 에 저장하지 않고 열 때마다 계산합니다. 미리
계산해 두면 어제 순위를 오늘 보여 주게 됩니다. 도구가 수천 건이 되면 스냅샷으로
옮기면 되고, 그때를 위해 가중치와 보정 기준이 결과에 함께 담겨 있습니다.

### 10단계 — ④ 멀티 LLM 품질검증 ✅

- [x] 관점 둘을 **서로 다른 모델**에
  | 관점 | 모델 | 묻는 것 |
  |---|---|---|
  | 내용 일관성 | `claude-opus-5` | 등록 내용끼리 앞뒤가 맞는가 |
  | 규정·보안 | `claude-sonnet-5` | 학내 규정과 보안상 빠진 것이 없는가 |
- [x] 판정이 갈리면 `NEEDS_HUMAN_REVIEW`. 다수결로 정하지 않습니다
- [x] BLOCKER 가 있으면 통과시키지 않습니다
- [x] 한쪽 호출이 실패하면 통과라도 사람 확인으로 돌립니다 (교차 검증이 안 된 결과)
- [x] 검토 화면에 관점별 모델·판정·지적 사항
- [x] `quality_reviews` 에 저장 (0017)

**바뀐 설계 — 테스트 케이스를 만들지 않았습니다.** 검증 대상을 도구의 *실행 결과*가
아니라 **등록 내용 자체**로 바꿨습니다. 플랫폼은 도구를 실행할 수 없어 케이스를
돌려 볼 방법이 없고, "이 입력에 이 출력이 나와야 한다"를 모델에게 판정시키는 것은
검증이 아니라 지어내기입니다.

대신 검토자가 스무 건을 훑다 보면 반드시 놓치는 것을 잡습니다 — "외부 전송 없음"에
체크해 놓고 기능 설명에는 번역 API 를 쓴다고 적힌 경우 같은 것.

**세 관점을 둘로 줄인 이유**: 규정과 보안은 학내 맥락에서 같은 질문입니다. 나눠
물으면 같은 지적이 두 번 나옵니다.

### 11단계 — 통합 표준화 (요구사항 3번) 🔜

**절반은 이미 됐습니다.** 중복 탐지가 처리 제안(합치기 / 역할 나누기)까지 냅니다.
남은 것은 **묶음** 단위입니다.

- [ ] 중복 판정이 누적된 도구들을 묶음으로 제시 ("이 3개는 같은 일을 합니다")
- [ ] 묶음의 기능 비교 표 — 어느 도구에 어떤 기능이 있는지
- [ ] 제안을 **개선 요청으로 전환**하는 버튼 (기존 개선 요청 흐름 재사용)
- [ ] 도구 상세에 "이 도구를 참고한 도구" / "이 도구가 참고한 도구"

`listDuplicateAnalyses(campusId)` 는 이 묶음 계산을 위해 미리 만들어 두었습니다.

## 4. 실제로 걸린 순서

```
6단계 배관        ✅  redact.ts 를 먼저 만들었습니다. 부르는 코드가 생기기 전에
  ↓                   경계를 세워야 우회할 수 없습니다
7단계 중복 탐지   ✅  글자 유사도(순수 함수)를 먼저, 모델은 그 위에
  ↓
8단계 위험도      ✅  기존 체크리스트 14항목에 그대로 얹었습니다
  ↓
9단계 매칭·순위   ✅  순위는 AI가 아니라 순수 계산이라 키 없이도 검증됐습니다
  ↓
10단계 멀티 LLM   ✅  검증 대상을 실행 결과에서 등록 내용으로 바꿔 풀었습니다
  ↓
11단계 통합 표준화 🔜  중복 판정이 쌓여야 묶음을 만들 수 있습니다
```

**최소선(6·7·8단계)을 넘겨 10단계까지 왔습니다.** 주요 기능 4개가 모두 살아 있고,
남은 11단계는 없어도 요구사항 3번의 절반(개별 도구 단위 통합 제안)은 이미 됩니다.

### 개인정보 처리 ✅

`src/adapters/ai/live/redact.ts` 가 모델로 나가는 **유일한 통로**입니다.
허용 목록 방식이라 도메인 타입에 필드가 생겨도 여기 적지 않으면 새지 않습니다.

- ✅ 나가는 것: 도구 이름, 소개, 기능 목록, 업무 흐름 설명, 데이터 분류 **이름**
- ❌ 나가지 않는 것: 실제 처리 데이터, 첨부파일 내용, 평가 원문, 문의 원문,
  감사 로그, **사람 이름**

사람 이름을 빼는 이유는 개인정보 때문만이 아닙니다. "김개발이 만든 도구"라고
보내면 모델 판단에 사람이 끼어듭니다. 도구를 도구로만 비교하려면 만든 사람이
누구인지 몰라야 합니다.

허용 목록을 통과한 뒤에도 연락처·주민등록번호·이메일·학번 패턴을 한 번 더
가립니다. 등록자가 설명에 실수로 적어 넣었을 수 있습니다. 막지 않고 **가립니다** —
예외를 던지면 도구 하나 때문에 분석 전체가 멈춥니다.
